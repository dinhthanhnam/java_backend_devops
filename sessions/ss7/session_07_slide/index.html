01

Tổng quan GitHub Actions & Kiến trúc Runner

© 2026 By Rikkei Academy - Rikkei Education - All rights reserved.

Vấn đề của quy trình thủ công

Tại sao không nên tự build & test ở local?

Quy trình thủ công & rủi ro

  • Lập trình viên quên chạy test hoặc build thử trước khi push.
  • Code lỗi biên dịch vẫn được merge vào nhánh chính.
  • “Chạy tốt trên máy tôi” — xung đột phiên bản JDK giữa các máy.

Hệ thống CI/CD tự động

  • Tự động chạy test & build tập trung mỗi khi push code mới.
  • Chặn merge code nếu build lỗi.
  • Đảm bảo môi trường biên dịch đồng nhất (Docker/VM chuẩn).

Lưu ý

Hệ thống CI/CD giúp loại bỏ hoàn toàn yếu tố chủ quan của con người trong khâu kiểm soát chất lượng code.

Khái niệm CI/CD

Trái tim của quy trình vận hành DevOps

🔄

Continuous Integration (CI)

Tự động hợp nhất code mới, chạy lint, biên dịch (compile) và chạy unit tests.
📦

Continuous Delivery (CD)

Đóng gói sản phẩm (JAR, Docker image) và sẵn sàng để deploy lên môi trường staging/production.
🚀

Continuous Deployment

Tự động triển khai code mới lên thẳng production mà không cần phê duyệt thủ công.
🛠️

Automation Tool

GitHub Actions tích hợp sâu vào GitHub repository, giúp kích hoạt pipeline từ các event của Git.

Kiến trúc GitHub Actions Runner

Cơ chế giao tiếp

Runner kéo job, không mở cổng

  • 1. Không mở cổng: Runner chủ động gửi request kéo công việc về (Long-polling), giúp máy chủ build không cần mở cổng SSH ra Internet.
  • 2. Cô lập: Runner tải mã nguồn về môi trường riêng để biên dịch rồi gửi log kết quả về cho GitHub Server hiển thị.

Hosted Runner vs Self-hosted Runner

GitHub-hosted Runner

  • Do GitHub quản lý hoàn toàn dưới dạng máy ảo (VM).
  • Máy ảo luôn sạch sẽ (khởi tạo mới tinh cho mỗi job).
  • Giới hạn cấu hình phần cứng (thường 2 vCPU, 7GB RAM).
  • Bị tính phí thời gian chạy (sau khi hết quota miễn phí).

Self-hosted Runner

  • Người dùng tự thiết lập trên VM/VPS hoặc máy vật lý riêng.
  • Giữ được bộ nhớ đệm (cache) giữa các lần build — build nhanh hơn.
  • Tùy biến cấu hình không giới hạn và miễn phí thời gian chạy.

Gợi ý

Đối với các ứng dụng Java Spring Boot đòi hỏi nhiều RAM khi biên dịch, sử dụng Self-hosted runner là giải pháp tối ưu chi phí.

Xây dựng cấu trúc Workflow CI/CD cơ bản

© 2026 By Rikkei Academy - Rikkei Education - All rights reserved.

Cấu trúc Workflow YAML

name
Tên của workflow
on
Sự kiện kích hoạt (push, pull_request)
jobs
Tập hợp các công việc chạy song song
runs-on
Loại Runner thực thi (ubuntu-latest, self-hosted)
steps
Các bước chạy tuần tự trong job
uses
Gọi Actions có sẵn từ Marketplace
basic-ci.yml yaml 
name: Basic CI
on: [push]
jobs:
  build-job:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Code
        uses: actions/checkout@v3
      - name: Run Script
        run: echo "Hello World"

Triển khai file Workflow hoàn chỉnh

Lưu tại thư mục .github/workflows/ci.yml

.github/workflows/ci.yml yaml 
name: QuickBite CI Pipeline

on:
  push:
    branches: [ main, develop ]
  pull_request:
    branches: [ main ]

jobs:
  test-code:
    runs-on: ubuntu-latest
    steps:
      - name: Clone source code from Git
        uses: actions/checkout@v3

      - name: Execute Shell Script
        run: |
          echo "Starting test suite..."
          echo "All tests passed successfully."

Thành công

Chỉ cần đẩy tệp này lên nhánh main, GitHub Actions sẽ tự động phát hiện và kích hoạt pipeline ngay lập tức.

Cơ chế điều phối và phân tách Jobs

Cơ chế Jobs song song và phụ thuộc

Job: Linter
Kiểm tra cú pháp
Job: Unit Test
Chạy bộ kiểm thử
needs
Job: Build & Packaging
Chỉ chạy nếu Linter & Test đạt

Từ khóa needs

Thứ tự phụ thuộc giữa các Job

  • Mặc định: Các jobs chạy song song độc lập.
  • Từ khóa needs: Tạo thứ tự phụ thuộc — job sau chỉ chạy khi job trước thành công.

Tối ưu

Không chạy build nếu linter hoặc test bị lỗi để tiết kiệm tài nguyên hạ tầng.

© 2026 By Rikkei Academy - Rikkei Education - All rights reserved.

Chiến lược Matrix

Chạy thử nghiệm trên nhiều phiên bản môi trường đồng thời

matrix.yml yaml 
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        java-version: [17, 21]
        os: [ubuntu-latest, windows-latest]
    steps:
      - uses: actions/setup-java@v3
        with:
          java-version: ${{ matrix.java-version }}

Ứng dụng thực tế

4 jobs kiểm thử đồng thời

  • Java 17 chạy trên Ubuntu
  • Java 17 chạy trên Windows
  • Java 21 chạy trên Ubuntu
  • Java 21 chạy trên Windows
  • Tiết kiệm công sức viết code cấu hình lặp lại.
  • Phát hiện sớm lỗi không tương thích phiên bản.

04

Biên dịch tự động Spring Boot với Gradle

© 2026 By Rikkei Academy - Rikkei Education - All rights reserved.

Cấu hình build Spring Boot với Gradle

gradle_ci.yml yaml 
jobs:
  build-spring-app:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: Setup Java JDK 17
        uses: actions/setup-java@v3
        with:
          java-version: '17'
          distribution: 'temurin'

      - name: Grant execute permission for gradlew
        run: chmod +x gradlew

      - name: Compile and Build JAR
        run: ./gradlew bootJar

Cảnh báo

Cần cấp quyền thực thi chmod +x gradlew trước khi chạy lệnh build, nếu không pipeline sẽ sập do lỗi Permission denied.

© 2026 By Rikkei Academy - Rikkei Education - All rights reserved.

Tối ưu hóa thời gian build với Cache

Tránh tải lại hàng trăm MB thư viện Gradle ở mỗi lần chạy

Không sử dụng Cache

  • Mỗi lần build, runner phải tải mới toàn bộ Spring dependencies từ Internet.
  • Thời gian build kéo dài (3 – 5 phút).
  • Tiêu tốn băng thông mạng vô ích.

Có sử dụng Cache

  • Tái sử dụng các thư viện đã tải từ các lần build trước.
  • Chỉ tải thêm các thư viện mới phát sinh.
  • Thời gian build giảm sâu (dưới 1 phút).

Mẹo

Sử dụng tính năng cache tích hợp sẵn của Action setup-java bằng cách cấu hình: cache: 'gradle'.

05

Chẩn đoán sự cố & Quản trị Log hệ thống CI/CD

© 2026 By Rikkei Academy - Rikkei Education - All rights reserved.

Quy trình chẩn đoán lỗi trong CI/CD

  1. 01

    Xác định Job bị lỗi

    Tìm job có biểu tượng dấu X đỏ trên tab Actions.

  2. 02

    Đọc log Step bị sập

    Mở Console của step lỗi để xem thông báo chi tiết.

  3. 03

    Phân loại lỗi phổ biến

    Lỗi cú pháp YAML, sai JDK, thiếu file cấu hình DB…

  4. 04

    Bật Debug log khi cần

    Đặt ACTIONS_RUNNER_DEBUG: true để xem hành vi Runner.

  • Permission denied: Quên chmod +x cho file gradlew.
  • Out of memory: Máy ảo Runner bị hết RAM vật lý khi build JVM.

Nền tảng tự động hóa CI/CD vững chắc

  • Tối ưu hóa pipeline biên dịch Spring Boot bằng cách bật cơ chế cache của Gradle.
